# Document storage

Documents are encrypted by the service with AES-256-GCM (`STORAGE_ENCRYPTION_KEY`) **before** they leave the process, then written by a store. Two stores exist, chosen with `STORAGE_DRIVER`:

| Driver | Use | Notes |
| --- | --- | --- |
| `local` (default) | Development | Files on local disk. **Single host only**: with several instances, each would have its own directory. |
| `s3` | Production | AWS S3 or any S3-compatible server. Shared by all instances, so more than one can run. |

## S3

Bucket contents are ciphertext only. S3 server-side encryption (`S3_SSE=AES256`, the default, or `aws:kms` with `S3_KMS_KEY_ID`) is a second layer on top of ours; `none` exists for local S3-compatible servers that do not support it.

### Bucket checklist (eu-central-1, Frankfurt)

- **Block all public access**: on.
- **Versioning: off.** With versioning on, deleting an object only adds a marker and the old bytes survive, which defeats erasure ([retention](retention.md)). The IAM policy below deliberately cannot read or change this setting, so check it in the console.
- Object Ownership: ACLs disabled. Default encryption: SSE-S3.
- Optional: a lifecycle rule to abort incomplete multipart uploads after one day, and a bucket policy denying requests where `aws:SecureTransport` is false.

### IAM

A dedicated user (or, in production, an instance role), separate from the face-match user. It needs object access only:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::<full-bucket-name>/*" },
    { "Effect": "Allow", "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::<full-bucket-name>" }
  ]
}
```

**`s3:ListBucket` is required.** Without it S3 answers `403 AccessDenied` instead of `404` when an object is absent, so every erased document would look like a storage failure (a 500) instead of a deleted one (a 410), and `storage:check` fails at "confirm it is gone". It does not let the service list your documents. With `S3_KEY_PREFIX`, narrow the object resource to `.../<prefix>/*` and add `"Condition": { "StringLike": { "s3:prefix": "<prefix>/*" } }` to the `ListBucket` statement. With `aws:kms`, also allow `kms:GenerateDataKey` and `kms:Decrypt` on that key.

### Configuration

| Variable | Meaning |
| --- | --- |
| `STORAGE_DRIVER=s3` | Use S3. |
| `S3_BUCKET` | The **full** bucket name. For an account-regional-namespace bucket that includes the account suffix. |
| `S3_REGION` | `eu-central-1`. |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Dedicated storage keys. Set both or neither. With neither, the AWS default chain is used (an IAM role in production). If `AWS_ACCESS_KEY_ID` (the face-match user) is also set, startup **fails with a clear message** rather than quietly using the wrong user; on a role, keep `AWS_ACCESS_KEY_ID` out of the environment. |
| `S3_SSE`, `S3_KMS_KEY_ID` | Server-side encryption mode. |
| `S3_KEY_PREFIX` | Optional folder inside the bucket: letters, digits, `.`, `_`, `-` and single slashes; `/` alone means none. |
| `S3_ENDPOINT`, `S3_FORCE_PATH_STYLE=true` | For S3-compatible servers. |

Real values go in `.env` only, never in `.env.example`.

### Trying it

`pnpm storage:check` writes, reads back, deletes and re-deletes one random object using your `.env`, and prints only pass/fail. Run it yourself once the bucket and user exist. A `403` almost always means the policy's bucket name or the `S3_BUCKET` value is wrong.

## What the tests do

The S3 unit tests use an in-memory fake client. `src/storage/s3.integration.spec.ts` runs the real AWS SDK against a local S3-compatible server (`docker compose up -d s3mock`, then `S3_TEST_ENDPOINT=http://localhost:9100 pnpm jest src/storage/s3.integration`) and is skipped otherwise. It refuses any endpoint that is not `localhost`/`127.0.0.1`/`::1`, and every test run ignores `.env` and forces local storage, so no test contacts AWS.

## Behaviour other code relies on

- A missing object (`NoSuchKey`/`NotFound`) is always `StoredObjectMissingError`, so readers answer `410 Gone`. A missing *bucket* (`NoSuchBucket`, e.g. a typo in `S3_BUCKET`) is deliberately not treated that way: it surfaces as a storage error.
- Delete is idempotent, so a retried erasure can finish.
- Erasure deletes files **before** database rows, in a transaction (see retention). With S3 that is two independent systems, so a crash between them leaves rows pointing at already-deleted objects, never the reverse; the next retention run completes it.
- Keys are generated by the service (`tenant/session/uuid`) and validated; unsafe keys are refused.

## Not covered

- Existing local files are not migrated to S3. Switching drivers on a deployment that already holds documents needs a copy step first.
- Cross-region replication, backups and bucket access logging are configured in AWS, not here.
